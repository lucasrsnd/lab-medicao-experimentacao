\title{Mineração de proxies DORA em repositórios open-source:
validade e sensibilidade das definições operacionais}
\author{Davi Érico\inst{1}, Gustavo Prehl\inst{1}, Lucas Resende\inst{1}}
\address{Engenharia de Software\\
Pontifícia Universidade Católica de Minas Gerais (PUC Minas)}

\begin{abstract}
This study proposes mining software delivery proxies from public GitHub
repositories using GitHub Actions. Releases, commit timestamps and workflow
runs support alternative operational definitions of DORA metrics. In the 300
selected repositories, the median project publishes one release every four
weeks, and lead time per release exceeds lead time per
commit (251 h versus 169 h). The two change failure rate proxies diverge
(medians 0.054 for CI failures and 0.292 for corrective releases), as do the
DORA categories: no project is Elite in frequency, while 77\% are Elite in CI
failure rate. Deployment frequency is positively correlated with both change
failure rate variants (Spearman $\rho = 0.182$ for CI failures and $0.567$ for
corrective releases), contrary to the DORA claim that speed and stability do
not compete. Across 12 tests with Holm correction, only lead time differs
significantly, by main language and by contributor quartile, with small to
medium effects. A single-rater validation, not linked to the frozen dataset, of the corrective
release heuristic on 283 releases yields precision 0.238, recall 0.870 and
F1 0.374, suggesting overestimation but not directly validating the dataset.
\end{abstract}

\begin{resumo}
Este estudo propõe minerar proxies de entrega de software em repositórios
públicos do GitHub que utilizam GitHub Actions. Releases, datas de commits e
execuções de workflows sustentam definições operacionais alternativas das
métricas DORA. Nos 300 repositórios selecionados, o
projeto mediano publica uma release a cada quatro semanas, e o lead time por
release supera o por commit (251 h contra 169 h). As duas variantes de taxa de
falha divergem (medianas de 0,054 para falhas de CI e 0,292 para releases
corretivas), assim como as categorias DORA: nenhum projeto é Elite em
frequência, enquanto 77\% são Elite em falha de CI. A frequência de deploy correlaciona-se
positivamente com as duas variantes de taxa de falha (Spearman $\rho = 0{,}182$
para falhas de CI e $0{,}567$ para releases corretivas), contrariando a
afirmação do DORA de que velocidade e estabilidade não competem. Em 12 testes
com correção de Holm, só o lead time difere significativamente, por linguagem
principal e por quartil de contribuidores, com efeitos pequenos a médios. Uma
validação com avaliador único da heurística de
release corretiva, não vinculada ao dataset congelado, em 283 releases,
resulta em precisão 0,238, recall 0,870 e F1 0,374; os rótulos sugerem
superestimação, mas não validam diretamente o dataset.
\end{resumo}
